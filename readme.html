How Selenium, Appium and Playwright reach the screen

Selenium and Appium send every command as a separate HTTP request through extra processes, and your test does the waiting. Playwright sends one message to an engine that keeps an open two-way line to the browser, and the engine does the finding, waiting and clicking.

HTTP, one request then one response Pipe, two-way, same machine WebSocket, two-way, over a network In memory, same process One OS process

The model every tool follows

Client libraryWhat your test calls: driver.click(), page.click(). It doesn’t control anything; it only sends messages.
ProtocolThe agreed message format and channel: W3C WebDriver over HTTP, or Playwright’s own protocol.
Something that can actCode with permission to read the UI and trigger real input: a driver, a helper app, or an injected script.

The tools differ in two things only: which protocol they use, and how many programs sit between your code and the screen.

The three architectures

Selenium
  • Request/response only: the browser can never speak first.
  • You hold an element ID, which goes stale if the page re-renders.
  • Waits run in your test, as repeated requests.
Appium
  • Same protocol as Selenium, more hops, so slower by nature.
  • Locators come from the accessibility tree, which is why accessibility IDs are the best mobile locators.
  • No auto-wait. iOS: XCUITest driver, WebDriverAgent, XCTest.
Playwright (JS)
  • The engine lives in your test process; no HTTP anywhere.
  • The browser pushes events (requests, dialogs, tabs).
  • No element IDs: the locator is re-resolved at every action.

Where WebdriverIO fits

WebdriverIO isn’t a fourth architecture. It’s a JavaScript/TypeScript client and full test framework that sits on top of the same WebDriver chains: browser drivers for web, the Appium server for mobile.

WebdriverIO (JS/TS)
  • Same chains below it as Selenium and Appium: the speed and protocol limits are the same.
  • Full framework built in: test runner, parallel runs, retries, reporters. Services start the browser driver or Appium for you.
  • Waits for you: element commands wait for the element to exist, and expect assertions retry until they pass or time out. Lighter than Playwright’s full actionability checks.
  • Browsers: can use WebDriver BiDi for events.
  • Deterministic and free at run time: no AI, no tokens.

One click, traced

Selenium 2+ HTTP round trips

Find and click are separate requests. If the page re-renders between them, the ID is stale.

Playwright 1 message, 1 reply

Find, wait, check and click happen inside the engine. Your test sends one message and waits for one reply.

Inside Playwright: one engine, different doors

Playwright is split into thin client objects (what you hold) and a server (the engine that does the work). They exchange small JSON messages such as {"id": 42, "guid": "frame@7c1e", "method": "click", "params": {...}}. Only the delivery changes by language, so behavior is identical everywhere.

JavaScript: 2 processes

Python, Java, .NET: 3 processes

Remote option: the engine runs on another machine (npx playwright run-server) and clients connect over a WebSocket (browserType.connect()), which is how Docker and grids work. Browsers are pinned to your Playwright version; upgrade Playwright, reinstall browsers.

Not covered by auto-wait

  • Reads like textContent(), isVisible(), count() answer immediately.
  • Business readiness (data still loading behind a ready button): wait on a result with a web-first assertion or waitForResponse.

Selenium’s equivalent

  • WebDriverWait(...).until(element_to_be_clickable) polls from your test, every 0.5 s by default.
  • Checks only displayed and enabled: no stability or overlay check, hence ElementClickInterceptedException.

WebDriver BiDi: Selenium and Appium go two-way

BiDi is the W3C standard that adds a two-way WebSocket to WebDriver. It runs alongside classic HTTP, so Selenium keeps its three processes: test, driver, browser.

What BiDi adds

  • Pushed events: console logs, JavaScript errors, network traffic, page loads.
  • Cross-browser network interception, replacing Chrome-only CDP.
  • User contexts: isolated sessions inside one browser.

What it doesn’t add

  • Auto-waiting: it’s a channel, not engine logic.
  • One message per action, or stale-proof locators: the API still hands you element IDs.
  • An integrated runner. In the Selenium world, auto-wait comes from frameworks on top: SHAFT, Selenide, WebdriverIO.

Why not just switch to WebSockets? WebDriver dates from around 2011, when HTTP was the universal choice and easy to implement in every language and to route through Grid and cloud providers. As a cross-vendor standard with huge backward compatibility needs, it can only move gradually, and the transport isn’t the main gap anyway: the API model is.

Interview answers

The architectureSelenium and Appium follow W3C WebDriver: the client turns each call into an HTTP request to a driver server, chromedriver for browsers, or the Appium server, which routes through a platform driver to a helper app using UiAutomator or XCTest. Because it’s request/response, you hold element IDs that can go stale and you write explicit waits. Playwright uses its own client/server design: in JS the engine runs inside the test process, in Python or Java it runs as a Node child process over a pipe, and it keeps a two-way connection to the browser plus an injected script in the page.
Why Playwright is faster and less flakyOne message per action instead of several HTTP round trips; the wait-and-retry loop runs next to the browser with millisecond precision and stronger checks, including stability and overlays; fresh browser contexts cost milliseconds; and events are pushed instead of polled. A slow app is still slow; the gain is in the overhead.
WebDriver BiDiClassic WebDriver is one-way. WebDriver BiDi adds a two-way WebSocket for events and network interception; Selenium is adopting it and Appium supports it partially. It brings the communication closer to Playwright’s, but not auto-waiting, which in the Selenium world comes from frameworks like SHAFT or Selenide.
Where WebdriverIO fitsWebdriverIO is a JavaScript framework on top of the same WebDriver protocol, so it drives browsers through their drivers and mobile apps through Appium. It adds what plain Selenium and Appium clients lack: a built-in runner, services that start the drivers, element commands that wait for elements, and retrying assertions. The protocol underneath is the same, so it’s closer to Playwright in experience, not in architecture.

10Common setup errors

  • Cannot use import statement outside a module: "type": "module" is missing from package.json.
  • Cannot find module '../pages/LoginPage': local imports need the .js extension.
  • page.goto: Invalid URL for "/": baseURL is missing for that project, or was put outside use.
  • Login fails in setup with an empty password: .env is missing, or SAUCE_PASSWORD isn't set (locally or as a CI secret).
  • getByTestId finds nothing on saucedemo: testIdAttribute: "data-test" is missing.
  • Executable doesn't exist: browsers aren't installed; run npx playwright install.
  • Workflow never runs: .github/workflows/ must be at the repository root.
  • API auth failed: API_PASSWORD is missing from .env or the CI secrets.
  • API tests get 403 on patch or delete: restful-booker expects the token as a Cookie: token=... header, which authRequest sends; use bookingApi, not the plain request.
  • Property 'createBooking' not found: the spec imports test from @playwright/test instead of fixtures/index.js.

11Notes and best practices

Best-practice checklists from the training, copied from the Test Automation Notes Library. Scan them before writing or reviewing code.

Playwright

Locators

  • Prefer getByRole or getByTestId; use CSS or XPath only as a last resort.
  • Set testIdAttribute in config when the app uses data-test instead of data-testid.
  • Inspect the real DOM before choosing a locator; don't assume labels or IDs exist.
  • Never await creating a locator; always await actions and assertions on it.
  • Fix strict-mode errors by narrowing the locator, not by adding .first().
  • For "a button inside a specific card," use filter({ hasText }) and chain the next locator.
  • Avoid position-based locators unless the position is what you're testing.
  • Assert toHaveCount before reading a list with allTextContents().

Actions, waiting, and assertions

  • Trust auto-waiting; don't add waits before clicks or fills.
  • Assert with web-first assertions (await expect(locator).toHaveText(...)), not by reading text and checking it once.
  • Never commit waitForTimeout; wait for the actual condition (URL, element, spinner hidden, response).
  • Use check()/uncheck() for checkboxes instead of click().
  • Don't use isVisible() or textContent() for checks or timing; they don't wait.
  • For optional popups, use a short bounded waitFor in try/catch, or addLocatorHandler.
  • Raise timeouts per assertion or per test (test.slow()), not globally; set actionTimeout so broken locators fail fast.

Page Object Model

  • One class per page; define locators once in the constructor as locator objects.
  • Name methods as user actions (login, addToCart), not low-level clicks.
  • Return the next page object from navigation methods, and always await them.
  • Turn shared UI parts (header, product card) into components held by pages.
  • Keep BasePage thin; avoid god classes full of helpers.
  • Keep assertions in tests; a small expectLoaded() readiness check is fine in a page object.
  • No sleeps or manual waits inside page objects.

Fixtures and login reuse

  • Provide page objects through fixtures instead of new in every test.
  • Import test and expect from your fixtures file, not from @playwright/test.
  • Log in once with a setup project and storageState, not through the UI in every test.
  • Start login tests logged out with an empty storageState.
  • Keep one state file per user or role, chosen with test.use().
  • Gitignore playwright/.auth/; session files are credentials.
  • Use testInfo in fixtures to generate unique, parallel-safe data.

Test data

  • Keep shared data in data/*.json, loaded through one helper.
  • Describe data-driven cases as rows (input + expected result) and loop to create one test per row, each with a unique title.
  • Use builders with overrides (buildCustomer({ zip: "" })) so each test shows only what's special about it.
  • Read secrets from environment variables, never from committed files.
  • Make every test create its own data; never depend on another test's leftovers.
  • Create and clean up server data in fixtures (setup before use(), teardown after).

Config, projects, and environments

  • Put runner options at the top level, browser options inside use, and variations in projects.
  • Use one project per browser or device, and limit expensive ones (mobile) with grep.
  • Choose the environment with an env variable, and fail fast on unknown names.
  • Keep secrets in a gitignored .env, commit .env.example, and use CI secrets in pipelines.
  • Load dotenv at the very top of the config.
  • Save common runs as npm scripts so everyone runs the suite the same way.
  • Never put URLs, environment names, or secrets inside tests.

Real-world UI situations

  • If an element is visible but "not found," check for an iframe and use frameLocator.
  • For new tabs, downloads, and file choosers, start waiting before the click (store, act, await).
  • Register dialog handlers before the action; remember dialogs are auto-dismissed by default.
  • Upload with setInputFiles (a path or an in-memory buffer); never drive the OS file picker.
  • Save downloads to testInfo.outputPath() so parallel tests don't collide.
  • Register page.route before goto, and use mocking for hard-to-reproduce states (empty, error, slow) while keeping real end-to-end tests too.

Visual comparisons

  • Expect the first run to fail while it creates the baseline.
  • Commit baselines and review them like code.
  • Never run --update-snapshots just to make a build green; check the diff first.
  • Prefer element screenshots; keep full-page checks for a few key pages.
  • Mask dynamic content and keep tolerance small (about maxDiffPixelRatio: 0.01).
  • Generate and compare baselines in the same environment (the Playwright Docker image or CI).
  • Keep visual tests few and focused; they complement functional tests.

CI

  • Put workflows in .github/workflows/ at the repository root.
  • Use npm ci, never npm install, in pipelines.
  • Take secrets from the pipeline's secret store, never from repo files or Docker images.
  • Always publish reports, even on failure (if: ${{ !cancelled() }}).
  • Match the Docker image tag to your @playwright/test version.
  • Shard only independent tests, and merge the blob reports into one HTML report.
  • Debug CI failures from the trace first; never "fix" flaky tests with retries alone.
  • Know the same pipeline in GitHub Actions, Jenkins, and Azure DevOps: same steps, different syntax.

API testing with Playwright

The request context

  • Put API tests in their own api project (own baseURL, testMatch, extraHTTPHeaders) so they never launch a browser.
  • Await both the call and response.json() in JavaScript.
  • Assert success with toBeOK() (Python: to_be_ok()); it prints the status and body when it fails.
  • Requests don't throw on 4xx/5xx by default, so assert status() explicitly in negative tests.
  • Send JSON by passing an object as data; Playwright sets the Content-Type for you.
  • Use params for query strings instead of building URLs by hand.
  • Validate the whole body's shape with toMatchObject + expect.any(Type), not just one or two fields.
  • Create your own data with unique values; don't rely on shared records like /booking/1.
  • Assert the API's real behavior, and note bugs (like 500 instead of 400) in a comment.
  • In Python, create the context in a session fixture with playwright.request.new_context(...) and dispose() it in teardown; status and ok are properties there, methods in JS.

Authentication

  • After login, check the token itself exists; some APIs return 200 even when login fails.
  • Fail fast with a clear error when auth fails, before the real test steps run.
  • Get the token once per worker (Python: per session) in a fixture; never log in inside every test.
  • Give tests an authenticated client fixture (authRequest) so test bodies contain no auth code.
  • Keep API URL and credentials in one config module, read from environment variables, never committed.
  • For every protected endpoint, test no token and an invalid token, and assert the refusal (401/403).
  • Verify the effect of writes with a follow-up GET, not just the status code.
  • Remember PUT replaces the whole resource and PATCH changes only the fields you send.
  • Treat every scheme as a header (Bearer, Basic, API key, cookie) and build it in one helper.
  • Dispose of request contexts you create yourself (await context.dispose() / context.dispose()).

Chaining calls and API clients

  • Chain calls by reading values (IDs, tokens) from one response and passing them to the next.
  • Wrap multi-stage flows in test.step() so the report shows exactly which stage failed.
  • Create one client class per resource (BookingApi); URLs, headers, and the auth choice live only there.
  • Have client methods return the response, so tests can assert both success and failure codes.
  • Keep assertions out of client classes; tests decide what "correct" means.
  • Provide clients through fixtures, never with new inside tests.
  • Use a factory fixture (createBooking) that creates data on demand, records the IDs, and deletes them all in teardown.
  • Throw a clear "Setup failed" error when test data creation fails, to separate setup problems from real failures.
  • Define response shapes once (bookingShape) and reuse them across tests.
  • Attach request/response details to the report on failure (testInfo.attach), but never tokens or passwords.

API setup combined with UI tests

  • Send only the part of the flow under test through the UI; do setup and cleanup through the API.
  • Remember page.request shares cookies with the page, so an API login makes the browser logged in too.
  • Use form: for classic HTML form endpoints and data: for JSON APIs.
  • Log in through the API in the setup project and save storageState from the request context (request.storageState()).
  • Keep one real UI login test so the login screen itself is still covered.
  • Create test data with API fixtures and delete it in teardown, even in UI tests.
  • Combine UI and API fixtures with mergeTests (JS) or a shared conftest.py (Python).
  • Capture the API response the page receives and assert the UI shows it, so a failure points to the right layer.
  • In Python, use page.expect_response(...) as a context manager and override browser_context_args to load a saved session.

JavaScript for automation

JS essentials

  • Use const by default, let only when reassigning, and never var.
  • Always compare with ===/!==; == converts types and gives surprises.
  • Remember empty arrays and objects are truthy; check items.length > 0.
  • Missing properties return undefined silently, so typos don't crash; double-check key names.
  • Use dot notation by default; use brackets when the key is in a variable or contains - (headers["Content-Type"]).
  • Prefer map/filter/find/some/every over manual loops.
  • Copy before sorting and pass a numeric comparator: [...prices].sort((a, b) => a - b).
  • Use ?? for defaults (keeps 0 and ""), and ?. only for genuinely optional data.
  • Use arrows for callbacks and test bodies; wrap a one-line returned object in parentheses: () => ({ ... }).

Classes & objects

  • Create objects with new; forgetting it throws.
  • Declare class fields without const/let (url = "/";).
  • Validate external input in the constructor with typeof and throw new Error(...).
  • Use static for factories, helpers, and shared constants, and call them on the class.
  • Never pass this.method as a callback; wrap it: (x) => this.method(x).
  • Use plain objects plus a factory function for data, and classes for behavior.

Encapsulation

  • Use #private for anything outside code shouldn't touch; _name is only a convention.
  • Expose data with getters; add setters only when assignment should be allowed and validated.
  • Inside setters, store into the #private field, never this.sameName, or you get infinite recursion.
  • Read-only getters ignore assignment silently in plain JS; don't rely on them to throw.
  • Return copies of private arrays and objects ([...this.#items]).
  • Freeze shared config and test data with Object.freeze (it's shallow, so freeze nested objects too).

Inheritance & polymorphism

  • Call super(...) before using this in a child constructor.
  • Use super.method() to extend a parent method instead of copying its code.
  • Don't make fields #private if children need them; children can't see them.
  • Write shared functions against method names, not instanceof chains.
  • Validate duck-typed dependencies once at the entry point (typeof reporter.logPass === "function").
  • Simulate abstract classes with new.target checks and throwing methods; compose shared UI components.

Errors

  • catch receives every error, so check instanceof and re-throw anything you didn't plan for.
  • Always throw Error objects, never strings.
  • Put cleanup in finally.
  • Build a small custom hierarchy and set this.name so reports show the right type.
  • Use { cause: err } when translating one error into another.
  • Test errors with expect(() => fn()).toThrow(...), passing a function, not a call.
  • Never wrap assertions in try/catch; it hides real failures.

Modules & npm

  • Use ES modules and named exports for your own code.
  • Write local imports with ./ or ../ and the .js extension; they're relative to the importing file.
  • Commit package.json and package-lock.json; never commit node_modules/ or .env.
  • Use npm ci in CI, and name common commands in package.json scripts.
  • Read settings from process.env through one config module that fails clearly when a variable is missing.
  • Keep test data in data/ and load it through one helper.

Async/await & Promises

  • Await every Playwright action, value read, and web-first assertion; a missing await gives no error, just wrong results.
  • Don't await locator creation or expect on plain values.
  • Wrap awaited code in try/catch; un-awaited failures escape it.
  • Use Promise.all for independent work, but keep actions on the same page sequential.
  • For events, store the wait before the action: store, act, await.
  • Never use forEach with async callbacks; use for...of.
  • Constructors can't be async; use a static async create() factory.
  • Never use fixed sleeps; wait for a condition.

Playwright Test runner

  • Import test and expect from your fixtures file once you have custom fixtures.
  • Put reusable setup in fixtures (test.extend), and keep hooks for file-local setup only.
  • Never use page in beforeAll; use browser or request there.
  • Use expect.soft only for independent checks on one screen, never for steps the test depends on.
  • Give every looped data-driven test a unique title.
  • Tag tests (@smoke) and run subsets with --grep, saved as npm scripts.
  • Keep every test independent, and generate unique data with testInfo.parallelIndex + a timestamp.
  • Use serial mode only when steps truly can't be separated.
  • Configure HTML + JUnit reporters and trace: "on-first-retry"; on failures, open the trace first.
  • Use UI mode and --debug while writing tests; never commit page.pause(); treat codegen output as a draft.

Python for automation

Classes & objects

  • Store data that must last between method calls on self; local variables disappear when the method ends.
  • Update class attributes (shared counters) through the class name: ClassName.count += 1, never self.count += 1.
  • Use @classmethod for factories (User.standard()) and return cls(...) so subclasses work too.
  • Use @staticmethod for helpers that need neither the object nor the class (is_valid_name()).
  • Always write __repr__ so logs and pytest failures show useful values; add __str__ for friendly output.
  • Add type hints everywhere (-> None for actions); they help the IDE, but Python doesn't enforce them.
  • Never use a mutable default (tags=[]); use None and create the list inside __init__.

Encapsulation & properties

  • Prefix internal attributes with _ and expose only what callers need, like a page object hiding its locators.
  • Use @property for read-only access, and change state only through clearly named methods (mark_passed()).
  • Add a setter only when assignment should be allowed, and validate inside it.
  • Assign through the setter in __init__ so invalid values are rejected at creation too.
  • Store in _x, expose as x; writing self.x inside its own setter causes infinite recursion.
  • Use computed properties (pass_rate) instead of storing values that can go stale.

Inheritance & super()

  • Put shared logic once in the parent (BasePage); children contain only their differences.
  • If a child defines __init__, call super().__init__(...) first, or parent attributes never get created.
  • Decide whether an override replaces the parent method or extends it with super().method().
  • Keep hierarchies shallow (two or three levels).
  • Inherit for "is-a" (a login page is a page); compose for "has-a" (a page has a header).
  • Python has no method overloading; a second def with the same name replaces the first, so use default parameters instead.

Polymorphism

  • Write code against shared method names or base types, not specific classes.
  • Replace if isinstance(...) chains with overridden methods, so a new class needs no edits elsewhere.
  • Overrides must keep the parent's signature and return type, or code using the parent breaks.
  • Duck typing is flexible but unchecked: a missing method only fails when called.
  • Implement dunders (__eq__, __len__, __iter__, __contains__) so your classes work with ==, len, for, and in.

Abstract classes & protocols

  • Use ABC + @abstractmethod when every child must implement something; mistakes then fail at object creation, not mid-test.
  • Use the template method pattern: the parent owns the workflow (open()), children fill in the steps (is_loaded()).
  • Return self from actions to allow method chaining.
  • Use Protocol for pluggable dependencies (reporters) that shouldn't need inheritance; it's checked by the IDE, not at runtime.
  • Keep interfaces small, and pass concrete dependencies in from outside (dependency inversion).

Dataclasses

  • Use @dataclass for data (users, payloads, config, expected results); use normal classes for behavior (page objects, clients).
  • Put required fields before fields with defaults.
  • Use field(default_factory=list) for list or dict defaults.
  • Validate and derive values in __post_init__.
  • Hide secrets with field(repr=False); exclude volatile fields (IDs, timestamps) from == with compare=False.
  • Use frozen=True for shared test data, and replace() to make modified copies.
  • Use asdict() for API payloads and a from_dict() classmethod that ignores unknown keys for responses.

SOLID

  • Single responsibility: one reason to change per class; if you describe it with "and," split it.
  • Open/closed: add features by adding classes or registry entries, not by editing if/elif chains.
  • Liskov: a child must work anywhere the parent is expected, with the same signature and no surprise errors.
  • Interface segregation: small interfaces, so no class carries fake methods it doesn't support.
  • Dependency inversion: depend on abstractions and inject dependencies through constructors or fixtures.

Exceptions

  • Catch specific exceptions only; never use a bare except: or except Exception: pass.
  • Never catch AssertionError in tests; it turns a failing test into a passing one.
  • Put cleanup in finally (or after yield in fixtures) so it always runs.
  • Fail fast with clear messages that say what's wrong and list the valid options.
  • Build one custom hierarchy under a base class (FrameworkError) so callers can catch the whole family.
  • Use raise NewError(...) from e when translating errors, to keep the original cause.
  • Use pytest.raises(X, match=...) when an error is the expected outcome.

Decorators

  • Remember that @dec above f means f = dec(f).
  • Follow the template: @functools.wraps(func), a wrapper with *args, **kwargs, and return func(...)'s result.
  • A decorator that catches errors must re-raise them, or tests pass when they shouldn't.
  • Decorators with settings (@retry(times=3)) need one extra outer function.
  • Retry unstable actions (API calls, data setup), never assertions.
  • When stacking, put the decorator that should "see everything" on top.

Modules & packages

  • Organize by responsibility: pages/, components/, models/, utils/, data/, tests/.
  • Add __init__.py to source folders.
  • Run from the project root, with pythonpath = . in pytest.ini; run scripts with python -m package.module.
  • Use one virtual environment per project, and commit a pinned requirements.txt (never the .venv/ folder).
  • Break circular imports between page objects with an import inside the method.
  • Never use from module import *.

pytest

  • Put setup in fixtures, with teardown after yield; share fixtures through conftest.py, never by importing it.
  • Use wide scopes only for read-only things (config, tokens); keep anything tests modify at function scope.
  • Use parametrize with readable ids for data-driven tests, never loops inside a test.
  • Register custom markers in pytest.ini and select suites with -m.
  • Use Playwright's expect(locator) for UI checks; plain assert for plain values.
  • Keep tests independent so they can run in any order and in parallel (-n auto).

Context managers

  • Use with for any setup/cleanup pair; cleanup is guaranteed even on errors.

  • Never act first and start waiting afterwards; the event may already be gone.

Best-practice checklists from the training, copied from the Test Automation Notes Library. Scan them before writing or reviewing code.

Appium

How Appium works, setup, and the first session

  • Know the chain: Python client → Appium server (HTTP, W3C WebDriver) → UiAutomator2/XCUITest driver → device.
  • Install drivers separately (appium driver install uiautomator2); the server alone can't drive anything.
  • Set ANDROID_HOME and JAVA_HOME correctly; most setup errors come from these two.
  • Check adb devices lists your device as device (not offline or unauthorized) before running tests.
  • Run appium driver doctor uiautomator2 whenever setup fails.
  • Use http://127.0.0.1:4723 with no /wd/hub; that suffix is from Appium 1.
  • Build capabilities with options classes (UiAutomator2Options), not raw dictionaries; they add the appium: prefix for you.
  • Use app to install an APK; use app_package + app_activity to launch an installed app, reading both from your own device with adb.
  • Treat no_reset = True as a local convenience only; it leaks state between tests.
  • Always quit() the session, in a yield fixture or a finally block.

Locators and Appium Inspector

  • Use Appium Inspector (desktop app or appium --use-plugins=inspector) to see the element tree and test locators before writing code.
  • Stop the Inspector session before running tests on the same emulator.
  • Follow the priority: accessibility ID → resource ID → UiAutomator → class name → XPath.
  • Avoid XPath on mobile; it's slow (Appium builds the whole screen's XML) and breaks when the layout changes.
  • Use the full resource ID (package:id/name), and confirm every attribute value in Inspector for your app version.
  • Reach off-screen elements with UiScrollable(...).scrollIntoView(...); mobile lists only render visible rows.
  • Use find_elements (returns an empty list, never raises) to check optional elements.
  • Search inside a container with parent.find_element(...) instead of long XPaths.
  • Store locators as (strategy, value) tuples and unpack them with *.
  • Remember get_attribute returns strings ("true", not True), and state reads like .text don't wait.
  • When key elements lack accessibility IDs, ask developers to add them; it helps both testing and accessibility.

Actions, explicit waits, and gestures

  • Remember Appium doesn't auto-wait: wait for the right condition before every action.
  • Use explicit waits (WebDriverWait + expected_conditions), and never mix them with implicit waits.
  • Wait for visibility before reading, element_to_be_clickable before tapping, and invisibility for spinners.
  • Put wait-then-act helpers (tap, type, visible, text_of) in a base screen so tests never call raw find_element.
  • Add StaleElementReferenceException to the wait's ignored_exceptions so re-renders retry instead of failing.
  • Call clear() before send_keys(), and hide the keyboard when it might cover the next element.
  • Use mobile: gesture commands (swipeGesture, scrollGesture, longClickGesture, dragGesture) for everyday Android gestures.
  • Use W3C Actions with a touch pointer for custom or cross-platform gestures; TouchAction is removed, so skip old tutorials.
  • Base coordinates on percentages of get_window_size(), never fixed pixels.
  • Give every scroll loop a maximum and a clear failure message, and never use time.sleep() for synchronization.

The mobile framework

  • Use the same architecture as web: config/, screens/, components/, data/, tests/, and fixtures in conftest.py.
  • Keep capabilities in a config file with one block per environment, chosen by an env variable (MOBILE_ENV); fail clearly on unknown names.
  • Load capabilities with UiAutomator2Options().load_capabilities(...), using full W3C names (appium: prefix).
  • Start the Appium session once (scope="session"), and reset the app before every test with an autouse fixture.
  • Pick the reset deliberately: restart (terminate_app + activate_app, keeps data), clear data (mobile: clearApp), or a new session (cleanest, slowest).
  • Build screen objects on BaseScreen: locators as class constants, user-action methods, a readiness check, and navigation that returns the next screen.
  • Break circular imports between screens with an import inside the method.
  • Provide starting points (catalog, logged_in) as fixtures, with credentials from data files or env variables.
  • Keep locators, waits, and capabilities out of test files.
  • Save a screenshot and page_source XML on every failure, using the pytest_runtest_makereport hook.
  • Skip removed APIs from old tutorials (driver.reset(), close_app(), TouchAction).

Real-world mobile situations

  • Test that app state survives backgrounding (background_app) and full restarts (terminate_app + activate_app); confirm with query_app_state (4 = foreground).
  • Grant permissions with autoGrantPermissions for feature tests; use mobile: changePermissions or the real dialog only when testing the permission flow.
  • Match system dialogs by text with textMatches("(?i)..."), because their wording changes across Android versions.
  • Hide the keyboard before tapping elements it might cover, and submit with mobile: performEditorAction when the app expects the keyboard's action key.
  • Use deep links (mobile: deepLink) to skip navigation you aren't testing, but keep one test that navigates normally.
  • Get deep link formats from developers or adb shell dumpsys package <package>, never by guessing.
  • For WebViews, switch to the WEBVIEW_... context, use web locators there, and always switch back to NATIVE_APP in finally.
  • Make sure WebView debugging is enabled in the test build and Appium can get a matching chromedriver (--allow-insecure=uiautomator2:chromedriver_autodownload).
  • Restore device-level settings (orientation, connectivity) in finally; app resets don't undo them.

CI, emulators, cloud device farms, and parallel runs

  • Start the emulator and the Appium server before tests, and wait until each is truly ready (poll Appium's /status).
  • Enable KVM on Linux CI runners; emulators are unusably slow without hardware acceleration.
  • Use an emulator runner action (e.g. reactivecircus/android-emulator-runner) and call one script file, so background processes like Appium run in the same shell.
  • Never commit APKs; download them from a build artifact or URL.
  • For cloud farms, upload the app, point at the vendor's hub URL, and add vendor options; credentials come from CI secrets, never config files.
  • Report each test's pass/fail to the cloud dashboard; it only sees commands, not your assertions.
  • In parallel runs, give every worker its own device (udid) and its own systemPort.
  • Run smoke tests on an emulator for every PR, full regression on real devices nightly, and choose devices from real user analytics.
  • Always upload the Appium log, JUnit report, screenshots, and page sources, even when tests fail.

Python for automation

Classes & objects

  • Store data that must last between method calls on self; local variables disappear when the method ends.
  • Update class attributes (shared counters) through the class name: ClassName.count += 1, never self.count += 1.
  • Use @classmethod for factories (User.standard()) and return cls(...) so subclasses work too.
  • Use @staticmethod for helpers that need neither the object nor the class (is_valid_name()).
  • Always write __repr__ so logs and pytest failures show useful values; add __str__ for friendly output.
  • Add type hints everywhere (-> None for actions); they help the IDE, but Python doesn't enforce them.
  • Never use a mutable default (tags=[]); use None and create the list inside __init__.

Encapsulation & properties

  • Prefix internal attributes with _ and expose only what callers need, like a page object hiding its locators.
  • Use @property for read-only access, and change state only through clearly named methods (mark_passed()).
  • Add a setter only when assignment should be allowed, and validate inside it.
  • Assign through the setter in __init__ so invalid values are rejected at creation too.
  • Store in _x, expose as x; writing self.x inside its own setter causes infinite recursion.
  • Use computed properties (pass_rate) instead of storing values that can go stale.

Inheritance & super()

  • Put shared logic once in the parent (BasePage); children contain only their differences.
  • If a child defines __init__, call super().__init__(...) first, or parent attributes never get created.
  • Decide whether an override replaces the parent method or extends it with super().method().
  • Keep hierarchies shallow (two or three levels).
  • Inherit for "is-a" (a login page is a page); compose for "has-a" (a page has a header).
  • Python has no method overloading; a second def with the same name replaces the first, so use default parameters instead.

Polymorphism

  • Write code against shared method names or base types, not specific classes.
  • Replace if isinstance(...) chains with overridden methods, so a new class needs no edits elsewhere.
  • Overrides must keep the parent's signature and return type, or code using the parent breaks.
  • Duck typing is flexible but unchecked: a missing method only fails when called.
  • Implement dunders (__eq__, __len__, __iter__, __contains__) so your classes work with ==, len, for, and in.

Abstract classes & protocols

  • Use ABC + @abstractmethod when every child must implement something; mistakes then fail at object creation, not mid-test.
  • Use the template method pattern: the parent owns the workflow (open()), children fill in the steps (is_loaded()).
  • Return self from actions to allow method chaining.
  • Use Protocol for pluggable dependencies (reporters) that shouldn't need inheritance; it's checked by the IDE, not at runtime.
  • Keep interfaces small, and pass concrete dependencies in from outside (dependency inversion).

Dataclasses

  • Use @dataclass for data (users, payloads, config, expected results); use normal classes for behavior (page objects, clients).
  • Put required fields before fields with defaults.
  • Use field(default_factory=list) for list or dict defaults.
  • Validate and derive values in __post_init__.
  • Hide secrets with field(repr=False); exclude volatile fields (IDs, timestamps) from == with compare=False.
  • Use frozen=True for shared test data, and replace() to make modified copies.
  • Use asdict() for API payloads and a from_dict() classmethod that ignores unknown keys for responses.

SOLID

  • Single responsibility: one reason to change per class; if you describe it with "and," split it.
  • Open/closed: add features by adding classes or registry entries, not by editing if/elif chains.
  • Liskov: a child must work anywhere the parent is expected, with the same signature and no surprise errors.
  • Interface segregation: small interfaces, so no class carries fake methods it doesn't support.
  • Dependency inversion: depend on abstractions and inject dependencies through constructors or fixtures.

Exceptions

  • Catch specific exceptions only; never use a bare except: or except Exception: pass.
  • Never catch AssertionError in tests; it turns a failing test into a passing one.
  • Put cleanup in finally (or after yield in fixtures) so it always runs.
  • Fail fast with clear messages that say what's wrong and list the valid options.
  • Build one custom hierarchy under a base class (FrameworkError) so callers can catch the whole family.
  • Use raise NewError(...) from e when translating errors, to keep the original cause.
  • Use pytest.raises(X, match=...) when an error is the expected outcome.

Decorators

  • Remember that @dec above f means f = dec(f).
  • Follow the template: @functools.wraps(func), a wrapper with *args, **kwargs, and return func(...)'s result.
  • A decorator that catches errors must re-raise them, or tests pass when they shouldn't.
  • Decorators with settings (@retry(times=3)) need one extra outer function.
  • Retry unstable actions (API calls, data setup), never assertions.
  • When stacking, put the decorator that should "see everything" on top.

Modules & packages

  • Organize by responsibility: pages/, components/, models/, utils/, data/, tests/.
  • Add __init__.py to source folders.
  • Run from the project root, with pythonpath = . in pytest.ini; run scripts with python -m package.module.
  • Use one virtual environment per project, and commit a pinned requirements.txt (never the .venv/ folder).
  • Break circular imports between page objects with an import inside the method.
  • Never use from module import *.

pytest

  • Put setup in fixtures, with teardown after yield; share fixtures through conftest.py, never by importing it.
  • Use wide scopes only for read-only things (config, tokens); keep anything tests modify at function scope.
  • Use parametrize with readable ids for data-driven tests, never loops inside a test.
  • Register custom markers in pytest.ini and select suites with -m.
  • Use Playwright's expect(locator) for UI checks; plain assert for plain values.
  • Keep tests independent so they can run in any order and in parallel (-n auto).

Context managers

  • Use with for any setup/cleanup pair; cleanup is guaranteed even on errors.
  • For Playwright expect_*: open the with, perform the action inside it, read .value after it.
  • Never act first and start waiting afterwards; the event may already be gone.
  • Use yield fixtures for per-test resources and @contextmanager for smaller blocks, with cleanup in finally.

  • Break circular imports between screens with an import inside the method.
  • Provide starting points (catalog, logged_in) as fixtures, with credentials from data files or env variables.
  • Keep locators, waits, and capabilities out of test files.
  • Save a screenshot and page_source XML on every failure, using the pytest_runtest_makereport hook.
  • Skip removed APIs from old tutorials (driver.reset(), close_app(), TouchAction).

Real-world mobile situations

  • Test that app state survives backgrounding (background_app) and full restarts (terminate_app + activate_app); confirm with query_app_state (4 = foreground).
  • Grant permissions with autoGrantPermissions for feature tests; use mobile: changePermissions or the real dialog only when testing the permission flow.
  • Match system dialogs by text with textMatches("(?i)..."), because their wording changes across Android versions.
  • Hide the keyboard before tapping elements it might cover, and submit with mobile: performEditorAction when the app expects the keyboard's action key.
  • Use deep links (mobile: deepLink) to skip navigation you aren't testing, but keep one test that navigates normally.
  • Get deep link formats from developers or adb shell dumpsys package <package>, never by guessing.
  • For WebViews, switch to the WEBVIEW_... context, use web locators there, and always switch back to NATIVE_APP in finally.
  • Make sure WebView debugging is enabled in the test build and Appium can get a matching chromedriver (--allow-insecure=uiautomator2:chromedriver_autodownload).
  • Restore device-level settings (orientation, connectivity) in finally; app resets don't undo them.

CI, emulators, cloud device farms, and parallel runs

  • Start the emulator and the Appium server before tests, and wait until each is truly ready (poll Appium's /status).
  • Enable KVM on Linux CI runners; emulators are unusably slow without hardware acceleration.
  • Use an emulator runner action (e.g. reactivecircus/android-emulator-runner) and call one script file, so background processes like Appium run in the same shell.
  • Never commit APKs; download them from a build artifact or URL.
  • For cloud farms, upload the app, point at the vendor's hub URL, and add vendor options; credentials come from CI secrets, never config files.
  • Report each test's pass/fail to the cloud dashboard; it only sees commands, not your assertions.
  • In parallel runs, give every worker its own device (udid) and its own systemPort.
  • Run smoke tests on an emulator for every PR, full regression on real devices nightly, and choose devices from real user analytics.
  • Always upload the Appium log, JUnit report, screenshots, and page sources, even when tests fail.

JMeter

Load tests with Apache JMeter: a test plan, properties per environment, non-GUI runs, and the HTML dashboard, against blazedemo.

1Prerequisites

  • Java 17 or newer (JMeter runs on Java).
  • Apache JMeter: download the binary .zip or .tgz from jmeter.apache.org and unzip it, e.g. to C:\tools\apache-jmeter or ~/tools/apache-jmeter.
  • Add JMeter's bin folder to your Path.
  • Optional: the JMeter Plugins Manager (a jar you drop into lib/ext) for extra graphs and thread groups.

Practice target: blazedemo.com, a demo flight-booking site built for load testing practice. Keep the load small; it's a shared public site.

2Create the project

Use the GUI only to build and debug the plan with 1 user. Real load always runs in non-GUI mode from the command line (step 6).

3Folder structure

The .jmx is XML that the GUI writes. Commit it like code. Load settings live in .properties files, so one plan runs with different loads per environment.

4Configuration files

5Build the test plan

Build these elements in the GUI (right-click → Add), in this order, then save as test-plans/blazedemo-booking.jmx.

  1. Test Plan: name it BlazeDemo booking.
  2. Config Element → HTTP Request Defaults: Protocol ${__P(protocol,https)}, Server name ${__P(host,blazedemo.com)}. Every request inherits these.
  3. Config Element → HTTP Cookie Manager: keeps each user's session cookies.
  4. Config Element → CSV Data Set Config: Filename ../data/routes.csv, Variable names empty (the first line is the header), Recycle on EOF True.
  5. Threads → Thread Group: Number of threads ${__P(users,1)}, Ramp-up ${__P(rampup,1)}, tick Infinite loop, tick Specify thread lifetime, Duration ${__P(duration,10)}.
  6. Inside the Thread Group, Sampler → HTTP Request Home: Method GET, Path /.
  7. HTTP Request Find flights: Method POST, Path /reserve.php, parameters fromPort = ${fromPort} and toPort = ${toPort}.
  8. Under Find flights, Assertions → Response Assertion: Text Response, Contains, pattern Flights from ${fromPort}.
  9. Under the Thread Group, Timer → Constant Timer: 1000 ms (think time between steps, like a real user).
  10. Listener → View Results Tree: for debugging in the GUI only. Disable it before load runs.

${__P(name,default)} reads a property from the command line or a .properties file, with a default for GUI runs. ${fromPort} is a variable from the CSV file. Relative CSV paths are resolved from the .jmx file's folder.

Run it once in the GUI (green play button) and check every sample is green in View Results Tree.

6First load run

  • -n non-GUI, -t test plan, -q properties file, -J one property.
  • -l raw results file, -e -o build the HTML dashboard into a folder, -f overwrite old results.

7Reporting and analysis

Open results/report/index.html. The key numbers to read:

  • Error %: should be 0. Any errors make the response times meaningless until fixed.
  • Response time percentiles (90th, 95th, 99th): what most users experience; more useful than the average.
  • Throughput: requests per second the system handled.
  • APDEX: a 0 to 1 satisfaction score based on response-time thresholds.
  • Response times over time graph: look for times rising as users ramp up.

Compare runs against agreed targets (for example: 95th percentile under 2 s, errors under 1%), not against feelings.

8CI and Docker

Check jmeter.apache.org for the current version number. Load tests usually run nightly or on demand, not on every pull request.

For Docker there's no official JMeter image; community images such as justb4/jmeter are widely used. Running in CI as above needs no image.

9You're done when…

  1. One GUI run with 1 user shows every sample green in View Results Tree.
  2. bash scripts/run.sh finishes in non-GUI mode and creates results/report/index.html.
  3. The dashboard shows 0% errors.
  4. -Jusers=3 changes the number of threads (check the dashboard's active threads graph).
  5. Breaking the assertion text makes errors appear in the dashboard.
  6. The CI workflow runs on demand and uploads the report.

10Common setup errors

  • Running load in the GUI: the GUI itself uses memory and CPU and distorts results; always use -n.
  • Results file ... is not empty or report folder exists: add -f, or delete results/.
  • CSV values show as ${fromPort} in requests: the CSV path is wrong (it's relative to the .jmx), or the header line doesn't match the variable names.
  • Properties have no effect: use ${__P(users,1)} in the plan; a plain ${users} reads a JMeter variable, not a property.
  • OutOfMemoryError: disable View Results Tree and other GUI listeners during load, or raise the heap: HEAP="-Xms1g -Xmx2g" before running.
  • All requests fail with SSL or host errors: check protocol and host values; host has no https:// prefix.
